#1  Timestamps are Europe/Lisbon wall time, not UTC            [critical] D-01
-------------------------------------------------------------------------------
Problem
  Two errors stacked. (a) OMIE's H{n} is hour n-1 of the CET/CEST market day,
  but the loader labelled it UTC. (b) The schema used naive TIMESTAMP, so
  DuckDB converted the tz-aware values into the OS session zone
  (Europe/Lisbon) and dropped the offset. Net effect: labels were +1 h off in
  winter and +3 h in summer, and the result depended on the build machine.
  Confirmed at the start of this work:
  SELECT current_setting('TimeZone') returned 'Europe/Lisbon'.

Fix
  - src/utils/timezone_utils.py
      * omie_hours_to_utc(): hour n = (local midnight of the market day, in
        Europe/Madrid, converted to UTC) + (n-1) hours. OMIE numbers hours
        sequentially in real time, so this is exact on 23- and 25-hour days,
        with no ambiguous or nonexistent wall-clock lookups.
      * market_window_utc(): the single date-window convention (see #7).
      * create_hour_index(): day boundaries are market days (local midnight),
        so 2022-01-01..2023-12-31 is exactly the 17,520 hours OMIE published.
      * add_time_features(): calendar features (hour, day_of_week, ...) are
        now computed in market local time. is_iberian_exception now starts at
        00:00 local on 2022-06-15 (22:00 UTC on 14 June), not at 00:00 UTC.
      * assert_utc_hourly(): asserts tz-aware UTC, on the hour, unique keys.
  - src/utils/db_schema.py: every timestamp column is TIMESTAMPTZ.
    migrate_naive_timestamps() upgrades an existing database. A PK column
    cannot be retyped in place in DuckDB 0.10, so each old table is copied to
    <table>_legacy_naive (if non-empty), dropped and recreated.
  - src/utils/db_utils.py: get_connection() runs SET TimeZone='UTC'. The
    manual asked for both measures ("belt and braces"); both are in place.
  - Database reloaded from the untouched raw files (decision B2).

Verified against the raw values the manual quotes
  2022-03-27 H1  258.17 -> 2022-03-26 23:00 UTC   (00:00 CET)
  2022-03-27 H2  242.01 -> 2022-03-27 00:00 UTC
  2022-10-30 H1  139.17 -> 2022-10-29 22:00 UTC   (00:00 CEST)
  2022-10-30 H2  105.10 -> 2022-10-29 23:00 UTC   (previously LOST)
  2022-10-30 H25 141.73 -> 2022-10-30 22:00 UTC   (previously DISCARDED)
  2023-10-29 H2    1.38 -> 2023-10-28 23:00 UTC   (previously LOST)
  A connection with the default Europe/Lisbon session reads the same
  instants (epoch values are identical), so the result no longer depends on
  the machine.

Consequences to be aware of
  - The panel's `hour` column is now true Iberian local hour (the old one was
    local in winter and local+1 in summer). The hourly profile still peaks at
    21:00 local (163.5 EUR/MWh) and bottoms out at 15:00 (100.3).
  - The pre/during split moved by 2 hours at the treatment boundary.
    Figures are almost unchanged: ES pre 211.81 (was 211.80), during 102.64
    (was 102.66). Coupling statistics are unchanged (corr 0.9953, 95.9% equal
    hours, ES>PT 102 h, PT>ES 613 h).
  - Notebooks, Power BI CSVs and dashboard.pbix have NOT been regenerated.
    Re-run notebooks/full_panel.ipynb to refresh them. It has local
    uncommitted edits, so it was left untouched.

#2  ML training set is empty; the script reports success          [high] D-14
-------------------------------------------------------------------------------
Problem
  create_all_features() ended with an unrestricted df.dropna(). The five
  all-NaN weather columns emptied the frame, and the prints still reported
  success. train_data.parquet and test_data.parquet were 0 rows x 39 columns.

Fix (mlops/models/training/feature_engineering.py) -- all three remedies
from the manual, plus two bugs found on the way
  - dropna(subset=feature_names + ['price_eur_mwh']): only columns the model
    uses can drop a row.
  - A missingness audit prints [WARN] for any column more than 50% NaN and
    says whether the model uses it.
  - create_all_features() raises ValueError when fewer than min_rows (default
    1) rows survive. prepare_train_test_split() raises on an empty input or an
    empty split.
  - NEW BUG FIXED: lags and rolling windows ran on the frame sorted by
    (country, timestamp) with no groupby. Portugal's first 168 hours of lags
    were therefore Spanish prices (cross-entity leakage). Both are now
    computed per country.
  - NEW BUG FIXED: __main__ took list(glob(...))[-1], an arbitrary file. On
    this disk that could be the 7-day pilot panel, too short for 168 h lags.
    It now takes --panel, or defaults to the panel with the most rows.
  - feature_names is reset on each call, so re-running does not duplicate it.
  - days_since_policy counts from 00:00 local on 2022-06-15.
  - Emoji output replaced with ASCII (see #9).
Result: 34,704 rows (33,262 train / 1,442 test), 24 features. The dropped
  rows are exactly the 168-hour warm-up per country (2 x 168 = 336). The old
  empty files were backed up to the session scratchpad before being
  overwritten.

#3  ENTSO-E and Open-Meteo never downloaded                       [high] D-15
-------------------------------------------------------------------------------
Fix
  - Open-Meteo downloaded: 7 locations, 2021-12-31..2023-12-31 UTC (one extra
    UTC day, because market day 2022-01-01 starts at 2021-12-31 23:00 UTC).
    122,808 rows = 7 x 17,544 hours.
  - ENTSO-E downloaded with the key in .env: day-ahead prices for the 12
    donor countries (FR DE IT NL BE AT DK SE NO FI PL CZ; 17,521 h each, no
    gaps) and physical flows for ES->PT, PT->ES, ES->FR, FR->ES
    (70,080 hourly rows = 4 x 17,520), 2022-01-01..2023-12-31.
  - src/data/entsoe_ingest.py changes needed to make the download correct:
      * PRICE_BIDDING_ZONES: DE, IT, DK, SE and NO are not single bidding
        zones, so requests for them return no prices. They now query DE_LU,
        IT_NORD, DK_1, SE_3 and NO_1 and store the result under the
        two-letter code.
      * The end date was exclusive (the last day was silently dropped). All
        dates are now inclusive days, turned into a half-open request window.
      * Chunks no longer overlap. Flows are chunked too and saved one file per
        pair (previously nothing was saved if ES->PT alone came back empty).
      * The client is created once. A missing API key now raises instead of
        being swallowed into empty frames. Failed chunks are listed at the end.
      * Flow parsing fixed. On the first run all 32 flow chunks failed inside
        entsoe-py 0.6.5 with "Length mismatch". ENTSO-E now sends flows as
        curve type A03, which omits positions that repeat the previous value,
        and 0.6.5's flow parser does not handle that (its generic parser
        does). download_cross_border_flows() now fetches the raw XML with
        EntsoeRawClient and parses it with the generic A03-aware parser.
        Cross-checked: ES->FR on 2022-06-15 gives the same values as the
        stock parser returned for that one-day request (721.12, 735.63,
        814.07 MW). ES<->FR switched to 15-minute resolution during 2023;
        the loader averages it to hourly MW.
      * Prices trimmed to the half-open window (entsoe-py includes the end
        hour; raw files from this run carry one extra hour, which the panel
        window excludes).
      * argparse --start/--end. The default window matches the OMIE data.
  - src/data/weather_ingest.py: timestamps stored tz-aware UTC at ingestion.
    Yearly chunks no longer share a boundary day (Open-Meteo's end date is
    inclusive). Failed chunks are reported. argparse --start/--end.
Not done: generation by fuel (D-15 consequence 4). No loader for the
  generation table exists and Part F #3 does not include it.
  download_generation_by_country() is available when needed.

    checks exactly what the loader loads (its old copy of the transform still
    had the D-01 bug).
  - Also: every table replacement is one transaction, rolled back on error,
    so a failure can no longer leave a table empty (the D-05 failure mode).
    It is implemented as "delete in-scope rows whose key is not in the new
    data, then INSERT ... ON CONFLICT (pk) DO UPDATE", because DuckDB 0.10
    rejects deleting and re-inserting the same primary key within one
    transaction (a documented index limitation, found here when the second
    reload failed). A regression test loads twice.

#6  DST fold discards two real prices per country per year    [med] D-03/D-04
-------------------------------------------------------------------------------
Fix: folded into #1, as the manual suggested.
  - H25 is read on autumn days. Every OMIE hour column that has a value is
    loaded.
  - The fold is two distinct UTC hours, so there is no key collision.
  - INSERT OR IGNORE is gone. Before writing, the loader de-duplicates
    identical rows from overlapping files, RAISES ValueError on conflicting
    prices for the same key, and asserts key uniqueness. A second real price
    can therefore never be silently discarded.
  - The loader warns if any market day's price count differs from its hour
    count (23/24/25). None did.
Result: 17,520 prices per country (was 17,516). 0 missing hours in the panel
  (was 4 per country).

#7  Inconsistent end-date semantics                              [med] D-13
-------------------------------------------------------------------------------
Fix
  One convention, defined once in timezone_utils.market_window_utc():
  start_date and end_date are inclusive market days, giving a half-open UTC

  the price, weather and flow queries all use it (build_panel._window_query).
  The ingestion scripts also use inclusive days with non-overlapping chunks
  (see #3).
  Test: test_panel_window_is_consistent_across_sources checks that the final
  day's weather and flows are present.

#11 Row-by-row inserts, ~1000x slower                            [low] D-11
-------------------------------------------------------------------------------
Fix: omie_wide_to_long() melts H1..H25 in one vectorised operation and
  computes timestamps arithmetically. Each table is written with one bulk
  set-based statement (INSERT ... SELECT ... ON CONFLICT). A full OMIE reload of 35,040 rows takes about 1.3 s; the
  whole load_to_db run takes about 2.6 s. The manual reports minutes.
